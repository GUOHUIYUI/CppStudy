# Day 19：从报错现象找到真正根因

> 所属阶段：C++基础迁移（Week 3）
> 日型：综合练习日
> 正课必修：约140～160分钟
> 巩固：约20～30分钟
> LeetCode：25分钟，单独计算
> 回练范围：Day 8、Day 15～18

今天不引入新的语言主题。目标是把已经见过的编译错误、链接错误、生命周期错误和接口歧义串起来，练习一套可重复的诊断方法。

不要靠连续随机修改直到程序“碰巧能编译”。每个故障先记录现象，再判断阶段，最后做最小修复。

## 今日目标

1. 根据错误出现阶段区分编译、链接和运行期问题；
2. 从第一条关键诊断信息开始定位，而不是被后续连锁报错淹没；
3. 修复声明/定义不一致、重复定义和缺失源文件；
4. 识别悬空引用、初始化顺序和重载歧义；
5. 为每个故障写出“现象—根因—最小修复”。

## 练习方法

每个任务都使用下面四步：

1. **预测**：它会在编译、链接还是运行阶段失败？
2. **复现**：实际构建，保留第一条有意义的诊断；
3. **解释**：指出哪个声明、定义、对象或调用发生了问题；
4. **修复**：只改导致问题的最小位置，然后重新构建。

在`root-cause-notes.md`中按下面格式记录：

```text
任务：
阶段：编译 / 链接 / 运行
关键诊断：
根因：
最小修复：
复测结果：
```

## 第一组：编译与链接故障

在`01_编译链接故障诊断`中完成。这里的代码片段是故意错误的，不要直接当作最终版本。

### 任务1：声明不可见

```cpp
int main()
{
    return add(2, 3);
}
```

先不包含头文件构建，再加入正确声明。观察错误发生在链接前还是链接后。

### 任务2：有声明但没有定义

`math_ops.h`：

```cpp
int add(int left, int right);
```

`main.cpp`正确包含头文件并调用，但暂时不要把`math_ops.cpp`加入项目。确认编译器接受调用，链接器却无法组成程序。

### 任务3：声明与定义签名不同

```cpp
// math_ops.h
double average(int total, int count);
```

```cpp
// math_ops.cpp（故意错误）
double average(double total, int count)
{
    return total / count;
}
```

两个函数不是“差不多相同”，而是两个不同签名。调用处需要的定义仍然不存在。

### 任务4：头文件中的重复定义

把普通非`inline`函数定义临时放进`math_ops.h`，让`main.cpp`和`report.cpp`都包含它。复现重复定义后，恢复为头文件声明、单个`.cpp`定义。

### 第一组完成标准

- 四种错误都真实复现过；
- 最终工程恢复为可编译状态；
- 每个错误都有一条根因记录；
- 能口头区分“声明不可见”和“定义不存在”。

## 第二组：生命周期与初始化

在`02_生命周期与接口歧义`中逐题实验。

### 任务5：返回局部对象的引用

```cpp
const std::string& makeLabel()
{
    std::string label{"ready"};
    return label; // 故意错误
}
```

局部字符串在函数返回时销毁，引用随后悬空。编译器可能警告，但运行表现不能作为正确性依据。最小修复是按值返回`std::string`。

不要为了“观察结果”多次读取悬空引用；未定义行为可能表现正常，也可能崩溃。

### 任务6：成员初始化顺序

```cpp
class Sample {
public:
    explicit Sample(int value)
        : scaled_{raw_ * 2}, raw_{value}
    {
    }

private:
    int scaled_;
    int raw_;
};
```

预测实际初始化顺序。打开高警告等级，找出为何仅调整初始化列表书写顺序还不够。最终让依赖关系清楚且不读取未初始化成员。

### 任务7：构造后才补齐状态

```cpp
DeviceConfig config;
config.setName("node-a");
config.setRate(100);
```

列出`config`刚创建但两个setter尚未执行时可能存在的状态。把必要值改为构造参数，让对象创建完成时就满足Day18的不变量。

## 第三组：接口歧义

### 任务8：默认参数与重载冲突

```cpp
void report(int value);
void report(int value, int precision = 2);

report(10); // 故意产生歧义
```

两个候选都能接收一个实参。选择一种最小且明确的接口：移除不必要重载，或取消产生冲突的默认参数。不要用强制类型转换掩盖接口本身的歧义。

### 任务9：`nullptr`选择正确重载

```cpp
void connect(int channel);
void connect(const char* address);
```

分别尝试`connect(0)`与`connect(nullptr)`，解释它们选择或尝试选择的语义。这里复习Day9，不要求设计所有权接口。

## 综合修复挑战

从Day17的配置解析工程复制一份到临时目录，故意制造并修复以下三个问题：

1. 头文件声明位于`device::config`，定义却落在全局命名空间；
2. 构造函数初始化列表与成员声明顺序相反，并制造依赖；
3. `RATE`失败时提前修改配置值。

每次只制造一个故障，修复后再进入下一项。不要在你已完成的Day17原目录中做破坏实验。

## 重要提醒

1. 第一条关键错误通常比后续连锁错误更接近根因；
2. 程序“这次运行正常”不能证明悬空引用安全；
3. 链接错误不要只在调用处反复改语法，应检查定义和项目文件；
4. 修复歧义应让接口意图更清楚，不是让编译器勉强选中。

## 快速自测

1. “identifier not found”和“unresolved external symbol”通常分别发生在哪个阶段？
2. include guard为什么不能解决跨翻译单元的普通函数重复定义？
3. 返回局部`std::string`引用后，引用为什么悬空？
4. 成员初始化顺序由什么决定？
5. 一个调用同时匹配两个重载时，应该优先检查调用处还是接口集合？

## 今日小结

1. 先判断失败阶段，再寻找对应范围的根因；
2. 声明解决编译可见性，定义满足最终链接；
3. 生命周期问题不能用一次运行结果证明安全；
4. 初始化依赖必须服从成员声明顺序；
5. 每次故障都应留下可复用的根因记录。
