# Day 20：发布命令行设备配置器 v1

> 所属阶段：C++基础迁移（Week 3）
> 日型：阶段项目收尾
> 正课必修：约180～210分钟
> LeetCode：30分钟，单独计算
> 综合范围：Day 1～19

今天不继续添加语法点，而是把前面分散完成的配置、解析、命名空间、错误结果和构造规则收束成一个可以独立构建、运行和说明的小程序。

核心目标不是把项目做大，而是让已有功能形成清楚、稳定的v1版本。

## 完成后的项目应具备

1. 清楚的头文件、源文件和命名空间结构；
2. 创建后即合法的`DeviceConfig`对象；
3. `NAME`、`RATE`、`STATE`、`SHOW`和`QUIT`命令；
4. 能区分空输入、未知命令、缺少参数和非法参数；
5. 失败时保持原配置不变；
6. 高警告等级构建通过，并保存测试与使用说明。

## 今天不做什么

- 不加入动态内存、智能指针和继承；
- 不引入JSON、数据库、网络或图形界面；
- 不为“像企业项目”增加无实际作用的抽象层；
- 不要求自动化单元测试框架，当前使用可重复的命令输入和结果记录；
- 不把LeetCode是否通过当作项目验收条件。

## 一、先确定最小模块边界

在`device-config-cli`中使用下面的结构：

```text
device-config-cli/
├── device_config.h
├── device_config.cpp
├── command_parser.h
├── command_parser.cpp
├── main.cpp
├── README.md
└── test-cases.md
```

推荐职责：

### `DeviceConfig`

- 保存名称、采样率和状态；
- 构造时建立合法初始状态；
- 修改接口拒绝非法值；
- 不读取终端输入，不负责打印命令错误。

### 命令解析模块

- 把一行文本拆为命令和参数；
- 调用配置对象的公开接口；
- 返回包含状态、字段和原因的结果；
- 不在每个错误分支里直接打印。

### `main.cpp`

- 创建初始配置；
- 循环读取命令；
- 处理`QUIT`；
- 调用解析模块；
- 在一个位置显示错误。

这三个部分已经足够。暂时不需要`Manager`、`Service`、`Repository`等额外类。

## 二、先写行为，再写实现

在编码前，用几句话固定命令语义：

```text
NAME <text>       名称长度1～16
RATE <integer>    采样率1～1000
STATE <value>     OFFLINE / IDLE / RUNNING
SHOW              显示当前配置
QUIT              退出程序
```

还需要明确空格和大小写。本版建议：

- 命令使用大写；
- 命令与参数之间至少一个空格；
- 参数前后的多余空格由你决定是否接受，但README必须写清；
- 名称暂不支持包含空格，避免把重点转成复杂文本解析。

如果你选择了不同但一致的规则，也可以，只要测试和README与实际行为相符。

## 三、实现顺序

### 步骤1：配置对象

先完成`DeviceConfig`，确认：

- 默认或带参数构造后对象合法；
- 名称、采样率和状态可以查询；
- 非法修改返回失败并保持旧值；
- 头文件没有`using namespace`。

### 步骤2：结果类型

复用Day17的核心结构，不必发明通用框架：

```text
status + field + reason
```

成功结果不需要冗长文本；失败结果要足够让`main()`给出可理解提示。

### 步骤3：单条命令

按`SHOW → NAME → RATE → STATE`的顺序逐个完成。每完成一条命令就构建并测试，不要等所有分支都写完才第一次运行。

### 步骤4：交互循环

最后加入循环读取和`QUIT`。EOF也应自然结束程序，避免输入流关闭后无限打印提示。

## 四、测试计划

在`test-cases.md`中至少记录15组测试。数量来自大纲，但不要用15个重复的正常输入凑数。建议分布如下：

### 初始状态与正常流程

1. 程序启动后`SHOW`；
2. 合法最短名称；
3. 合法16字符名称；
4. `RATE 1`；
5. `RATE 1000`；
6. 三种合法状态；
7. 多次修改后`SHOW`。

### 失败与边界

8. 空行；
9. 未知命令；
10. `NAME`缺少参数；
11. 名称超过16字符；
12. `RATE`缺少参数；
13. `RATE 0`；
14. `RATE 1001`；
15. `RATE abc`；
16. 非法状态；
17. 输入流结束或`QUIT`。

你不必机械采用以上编号，但最终至少应覆盖正常、边界和失败三类。每组记录：

```text
输入：
预期：
实际：
是否通过：
```

对非法修改，应紧接着执行`SHOW`，确认旧值没有被部分改变。

## 五、构建与警告

项目已经配置C++17和高警告等级。完成代码后执行一次完整重新生成，而不只是依赖增量构建。

处理警告时重点检查：

- 有符号与无符号尺寸比较；
- 未使用的局部结果；
- 声明与定义不一致；
- 初始化列表顺序；
- 控制路径缺少返回值。

“0 warning”不代表程序逻辑必然正确，但未解释的警告不应被直接忽略。

## 六、README只回答使用者需要的问题

`README.md`保持简短，至少包括：

1. 项目做什么；
2. 如何在Visual Studio中构建；
3. 支持哪些命令；
4. 参数范围和输入规则；
5. 一段示例会话；
6. 当前版本没有实现什么。

不需要复制课程正文，也不需要写尚未存在的未来架构。

## 七、最终自查

### 功能

- 合法命令产生正确结果；
- 四类错误能够区分；
- 非法修改保持原值；
- `QUIT`和EOF都能结束循环。

### 结构

- 类和函数位于清楚的命名空间；
- 头文件只暴露必要接口；
- 普通函数定义没有重复放入公共头文件；
- `.cpp`首先包含自己的头文件。

### 交付

- Debug x64完整构建通过；
- 没有未解释警告；
- 至少15组测试有记录；
- README与实际程序一致；
- 没有提交`.vs`、`x64`、`.obj`或`.exe`。
